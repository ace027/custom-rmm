# Dev environment

A Docker Compose stack runs Timescale (Postgres 17), NATS (JetStream and
WebSocket), nginx with TLS, and the `rmm-server` processes `api`, `ingest`,
`authd` and `migrate`.

## Prerequisites

- Docker with the Compose plugin
- `openssl`, `curl`, `python3`
- Rust toolchain from `rust-toolchain.toml`
- `sqlx-cli` for refreshing offline query data:
  `cargo install sqlx-cli --no-default-features --features rustls,postgres --locked`

## Commands

- `scripts/dev-up.sh` creates `deploy/.env` from `deploy/.env.example` if
  missing, generates dev certificates, builds `rmm-server:dev` and starts the
  stack, waiting until every service is healthy.
- `scripts/smoke-dev.sh` runs `dev-up.sh` and asserts TLS, the NATS WebSocket
  upgrade through nginx, JetStream health, the timescaledb extension and the
  schemas `tenant`, `msp`, `ts_private`, `rmm`.
- `scripts/dev-certs.sh [--force]` regenerates the dev CA and server cert.
- Reset all data: `docker compose -f deploy/compose.yaml down -v`.

## Ports

| Port | Service | Bound to |
|------|---------|----------|
| 443 (`RMM_HTTPS_PORT`) | nginx TLS: `/healthz`, `/api/`, `/v1/enroll`, `/nats` (WebSocket) | all interfaces |
| 5432 | Timescale | 127.0.0.1 |
| 4222 | NATS client | 127.0.0.1 |
| 8222 | NATS monitoring | 127.0.0.1 |

nginx rate-limits the public paths per client IP and answers 429 beyond the
limits: `/nats` 10 requests/s (burst 20) and 50 concurrent connections,
`/v1/enroll` 5 requests/s (burst 10). The static NATS users (`api`, `ingest`,
`authd`, `sys`) accept plain TCP connections only and are refused on the
WebSocket listener.

## Environment variables

Defined in `deploy/.env` (dev-only values; never reuse them elsewhere):
`RMM_PG_PASSWORD`, `RMM_NATS_{API,INGEST,AUTHD,SYS}_PASSWORD`,
`RMM_HTTPS_PORT`, `RMM_DATABASE_URL`, `RMM_NATS_URL`,
`RMM_AUTHD_ISSUER_SEED` and `RMM_AUTHD_ISSUER_PUBKEY` (generated by
`dev-up.sh`), and optionally `RMM_ROOT_PUBKEYS` / `RMM_ROOT_THRESHOLD` for
trust artifact uploads.

Server processes read `RMM_API_LISTEN` (default `0.0.0.0:8080`),
`RMM_HEALTH_LISTEN` (ingest `0.0.0.0:8081`, authd `0.0.0.0:8082`),
`RMM_NATS_USER`, `RMM_NATS_PASSWORD`, `RMM_DATABASE_URL`, `RUST_LOG` and
`RMM_LOG_FORMAT=json`. authd also reads `RMM_NATS_SYS_USER`,
`RMM_NATS_SYS_PASSWORD` and `RMM_AUTHD_ISSUER_SEED`.

If port 443 is taken, set `RMM_HTTPS_PORT` (for example `8443`); the smoke test
honours it.

### Proxied networks

The image build passes `HTTPS_PROXY` through as a build argument. For a
TLS-intercepting proxy set `RMM_EXTRA_CA_FILE` to the CA bundle; it is mounted
as a build secret and installed before `cargo build`. Without a proxy nothing
is needed (an empty file is used). `dev-up.sh` defaults `RMM_EXTRA_CA_FILE` to
`/root/.ccr/ca-bundle.crt` when that file exists. The image is built with
`docker build --network host` because Compose v5 would otherwise require
explicit buildx entitlements.

## Trusting the dev CA

Certificates live in the gitignored `deploy/dev/certs`. Trust `ca.pem` in your
OS store, or pass `--cacert deploy/dev/certs/ca.pem` to curl. The server key is
mode 0644 so the nginx container can read it; this is acceptable only for the
gitignored local dev directory. The CA key is mode 0600.

## sqlx offline data

`rmm-db` uses `sqlx::query_scalar!`. With the stack up run:

```
DATABASE_URL=postgres://rmm:<RMM_PG_PASSWORD>@127.0.0.1:5432/rmm cargo sqlx prepare --workspace
```

and commit `.sqlx/`. Docker builds use `SQLX_OFFLINE=true`.

## NATS authentication (auth callout)

The service users `api`, `ingest`, `authd` (account `RMM`) and `sys`
(account `SYS`) log in with the static passwords from `deploy/.env`; `api`
and `ingest` may not publish or subscribe on `$SYS.>`, so only `authd` can
see or answer callout requests. Every other connection (the agents) goes
through the NATS auth callout (`authorization.auth_callout` in
`deploy/nats/nats.conf`):

1. NATS sends a signed `authorization_request` JWT to `$SYS.REQ.USER.AUTH`.
   `always_enable_nonce` makes the server send a nonce to every client; the
   agent signs it with its device key, whose public half is its user nkey.
2. `rmm-server authd` checks the nonce signature, looks the agent up by
   public key in a `Scope::Service("authd")` transaction (2 s statement
   timeout), requires agent and client status `active`, updates
   `last_seen` and writes an audit row (`nats.auth.allow` or
   `nats.auth.deny`, actor `authd`).
3. It replies with an `authorization_response` signed by the issuer account
   key. On allow this carries a user JWT for account `RMM` that expires after
   one hour, is valid for WebSocket connections only, and allows only the
   agent's own subjects (`telemetry.<client>.<agent>.>`,
   `result.<client>.<agent>`, `shell.<agent>.*.out`, `svc.trust.latest`, its
   JetStream `CMD` consumer, and subscriptions on `_INBOX_<agent>.>` and
   `shell.<agent>.*.{in,ctl}`). Any error is a deny with the generic message
   `not authorized`; the reason is only logged and audited.

When the API revokes an agent it publishes `{agent_id, nkey}` on
`rmm.internal.agent.revoked`. authd then uses the `sys` user to find the
agent's connections with `$SYS.REQ.SERVER.PING.CONNZ` (filter `user`) and
kicks each with `$SYS.REQ.SERVER.<server_id>.KICK`, once at once and again a
second later.

authd `/healthz` (port 8082) returns 200 only while both NATS connections are
up and the database answered its 15 s probe within the last 30 s. With the
database down authd keeps running and denies every agent.

### Dev issuer

The callout issuer is an account nkey. `dev-up.sh` generates one on first run
with `docker run --rm rmm-server:dev gen-nkey --type account` and stores
`RMM_AUTHD_ISSUER_SEED` (given to authd) and `RMM_AUTHD_ISSUER_PUBKEY` (given
to NATS) in `deploy/.env`, which it makes mode 0600. To rotate, blank
`RMM_AUTHD_ISSUER_SEED` and run `dev-up.sh` again. Plain
`rmm-server gen-nkey --type user` prints a user key pair the same way.

## Telemetry flow

Agents publish on `telemetry.<client>.<agent>.<kind>` over the WebSocket:
heartbeats (`hb`, core NATS), metric batches (`metric`) and inventory (`inv`),
both JetStream publishes with a UUIDv7 `Nats-Msg-Id`. Payloads are CBOR
(`rmm_proto::telemetry`) and carry no client or agent id: ingest takes both
from the subject, which authd's per-agent JWT makes unforgeable, and checks
them against `tenant.agent` (active, and the same client). Anything else is
terminated and counted.

`rmm-server ingest` creates the stream `TELEM` (`telemetry.>`, file storage,
3 days, 2 minute duplicate window) and the durable pull consumer `ingest`
(explicit acks, 30 s ack wait, 5 deliveries). It fetches up to 500 messages or
1 s, then writes the batch in one `Scope::Service("ingest")` transaction as
role `rmm_ingest`: heartbeats update `tenant.agent.last_seen`, a changed
inventory updates `tenant.device` and writes one `inventory.changed` row in
`tenant.device_event` (before/after hold exactly the changed columns), metric
samples go to `ts_private.metrics` (samples older than 7 days or more than 5
minutes ahead are dropped and counted). Messages are acknowledged after the
commit; with the database down they are naked with a 5 s delay and `/healthz`
(port 8081) turns 503. Counters are logged every 60 s.

Debug agent builds read `RMM_AGENT_TELEMETRY_INTERVALS` (decimal seconds, for
example `hb=2,metric=3,inv=5`) instead of the 30 s / 60 s / 6 h defaults.
Intervals are clamped to at least 0.01 s; collecting one metric sample blocks
the agent for about 200 ms, so it cannot publish faster than about 5 batches
per second.

Read metrics the way the API does, through the scoped view (no grants on
`ts_private` for `rmm_api`):

```
docker compose -f deploy/compose.yaml exec -T timescale psql -U rmm -d rmm -c "
BEGIN; SET LOCAL ROLE rmm_api; SET LOCAL rmm.service = 'off';
SET LOCAL rmm.client_ids = '{<client-uuid>}';
SELECT time, metric, value FROM tenant.metrics_v
WHERE device_id = '<device-uuid>' ORDER BY time DESC LIMIT 20; COMMIT;"
```

`scripts/e2e-telemetry.sh` enrolls an agent and checks heartbeat, inventory
and event, metrics, tenant isolation of `metrics_v`, a RAM change becoming an
event, and ingest keeping up with a fast agent and a 10000 sample burst.

`scripts/e2e-offline.sh` stops nginx for 60 s while an agent runs with fast
intervals, restarts it, and checks that every queued sample arrives, that
`ts_private.metrics` has no duplicate `(time, metric)` rows, that a hard-killed
agent restarted while offline still delivers its queue exactly once, and that
`agent-store.db` holds no metric name in clear.

## Agent local store and offline queue

The agent keeps an encrypted SQLite store in its state dir (default:
platform specific; `--state-dir` overrides it):

- `agent-store.db` (plus `-wal` and `-shm`): the outbox of metric and
  inventory messages not yet acknowledged by the server, the command replay
  cache, trust sequence floors and the trust and policy caches. Values are
  sealed with XChaCha20-Poly1305; row ids, subjects, priorities, timestamps and
  sizes are readable.
- `store.key`: the random 32-byte store key, protected like `agent.key`
  (0600 on Unix, DPAPI on Windows). If the database exists without this file
  the agent refuses to start rather than begin a new store; delete both files
  to reset a dev agent.

Metrics and inventory are written to the outbox first and deleted only after the
JetStream ack, so an outage or agent restart loses nothing. The outbox holds up
to 50000 rows or 64 MiB; when full the oldest metric batches are dropped first
(inventory is kept) and the drops are logged. After a reconnect it drains by
priority (inventory, then metrics) and then by age. Ingest dedupes by `msg_id`
in `ts_private.ingested_msg` (kept 7 days), so re-sent rows are written once.

Inspect the queue length (row counts are not secret; payloads are):

```
sudo python3 -c 'import sqlite3,sys; c=sqlite3.connect(sys.argv[1]); \
print(c.execute("select priority, count(*) from outbox group by priority").fetchall())' \
  <state-dir>/agent-store.db
```

Or with the sqlite3 CLI: `sudo sqlite3 <state-dir>/agent-store.db 'select count(*) from outbox'`.

## Technician tokens in dev

The api service runs with `RMM_AUTH_ALLOW_DEV=1`, audience `api://rmm-dev`,
and a dev RS256 key pair that `dev-up.sh` generates in the gitignored
`deploy/dev/auth` (mounted read-only at `/run/rmm-auth`). Mint a token and
call the admin API:

```
TOKEN=$(docker compose -f deploy/compose.yaml exec -T api \
  rmm-server dev-token --role RMM.Admin --sub me)
curl --cacert deploy/dev/certs/ca.pem -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -X POST \
  -d '{"client_id":"<uuid>","site_id":"<uuid>","expires_in_hours":1,"max_uses":1,"allow_reattach":false}' \
  https://localhost:${RMM_HTTPS_PORT:-443}/api/v1/enrollment-tokens
```

The dev issuer must never be enabled outside the dev stack. The private key
is mode 0644 only because the server containers run as uid 10001.

## End-to-end enrollment test

`scripts/e2e-enroll.sh` brings the stack up, creates two clients with a site
each via `psql`, and drives a debug Linux agent
(`RMM_AGENT_EXTRA_CA=deploy/dev/certs/ca.pem`) through enrollment, connection
over `wss://localhost:$RMM_HTTPS_PORT/nats`, token reuse, cross-tenant
publish and subscribe (via `natsio/nats-box` with the agent's seed from
`scripts/nkey-seed.py`), plain-TCP refusal, revocation kick, reattach and
clone flagging. It runs the agent as root in a private mount namespace with a
fake `/sys/class/dmi`, so it needs root or passwordless sudo. It leaves the
stack running.

## Dev trust chain

`scripts/dev-trust.sh` (run by `dev-up.sh`) uses `rmm-sign` with throwaway keys
(passphrase `dev-only`) to create `deploy/dev/trust/`: `root.age`,
`catalog.age`, `command.seed` (the API's online command key, mounted read-only
at `/run/rmm-trust`), a root-signed `manifest.env` (capability ceiling
`service`, `files.write`), an empty `revocations.env` (45-day expiry) and the
signed `printing.spooler-restart.env`. It is idempotent; `--force` re-signs.
`dev-up.sh` writes `RMM_ROOT_PUBKEYS` into `deploy/.env` and uploads the
documents through the API. Agents for the e2e scripts are built with that
`RMM_ROOT_PUBKEYS`. `scripts/e2e-actions.sh` proves success, rollback,
revocation and forged-result handling.
