# custom-rmm

## What This Is
Security-first RMM backend as a Rust Cargo workspace: Windows-first endpoint agent, watchdog/updater, session helper, server (API, ingest, NATS auth callout, migrations), shared protocol/trust crates and a YubiKey signing CLI. The trust chain guarantees a compromised server cannot run arbitrary code on endpoints. The web UI lives in a separate monorepo; this repo exports an OpenAPI spec via utoipa. Design source: .planning/explorations/2026-10-31-rmm-backend-phase1-design.md; product spec: RMM Platform Spec.md.

## Core Value
Kaseya-proof by construction: everything that executes on an endpoint traces to an offline root key and a YubiKey touch, or, for remote shells, to the technician's own hardware key.

## Who It's For
Dean IT Services technicians (through the external React console), the MSP owner as signing-key custodian, and internal Windows endpoints during the parallel run alongside NinjaOne.

## Constraints
- Rust stable; tokio, async-nats (websockets feature), axum, sqlx (offline mode), utoipa, windows-rs, portable-pty, openpgp-card
- No AI on endpoints; agent executes only signed catalog actions, signed scripts and co-signed shells
- The server can invoke signed definitions but never create them; it holds no signing key
- Agent connects outbound only: NATS over WebSocket, TLS 443
- No obfuscation, packers or -EncodedCommand; prefer OS APIs over shelling out; never touch LSASS or inject into processes
- Postgres + TimescaleDB with RLS; client_id on every tenant table (msp.* tables are the documented exception)
- Windows 10 1809+ / Server 2019+ for the agent
- One instance per MSP; no company names in code; branding from config
- No fixed deadline: quality and security gates over speed

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Approach B (balanced) from the design exploration | Meets every non-negotiable while avoiding risky toolchain dependencies; leaves slots (alg fields, KeyStore trait, e2e_pubkey) for the ambitious upgrades | Pending |
| Remote shell requires a technician WebAuthn co-signature verified by the agent | A shell is arbitrary execution; the server alone must not be able to open one | Pending |
| Hardware-only authenticators for shell co-sign (AAGUID allowlist) | Synced passkeys can leave the device | Pending |
| YubiKey signing via OpenPGP applet Ed25519 with openpgp-card crates; PIV Ed25519 (fw 5.7+) is the fallback | Works on all YubiKey 5; yubikey.rs PIV lacks Ed25519 and is unaudited | Pending |
| Deterministic CBOR envelopes, signatures over a fixed digest | Binary-native for NATS, no float or number canonicalization issues; fits card EdDSA input size | Pending |
| NATS agent auth via a Rust auth callout issuing scoped JWTs | Instant revocation from DB status; no separate NATS user store | Pending |
| Agent key Ed25519 wrapped by DPAPI in phase 1; TPM later | TPM providers lack Ed25519 and many VMs lack vTPM | Pending |
| Metrics in a private compressed hypertable behind scoped views | TimescaleDB does not support RLS on compressed chunks | Pending |
| App-level AEAD local store instead of SQLCipher | Pure Rust, cross-compiles cleanly; avoids OpenSSL | Pending |
| CI uses both cargo-xwin cross-compile and a native Windows runner | Fast PR feedback plus real tests for DPAPI, SCM and ConPTY | Pending |
| Entra ID OIDC for technician login; recordings retained 1 year; revocation mirror deferred | Resolved in the design discussion | Pending |
| Root key generated air-gapped, age-encrypted on two USB sticks (safe + offsite) | Backupable offline custody with a documented ceremony | Pending |
| Foundation is broken into 9 Triad phases (design milestones M0-M8); product phases 2-6 come later | Triad phases are small; product roadmap: 2 policy + alerts + AI shadow, 3 catalog + autonomy gate, 4 MCP + diagnosis, 5 file transfer + remote desktop + Linux, 6 patching + macOS + Authenticode; gate before first client | Pending |

## Architecture Influences
Shared crates (proto <- trust <- recipe) used by both agent and server; platform-agnostic agent core behind a Platform trait with cfg(target_os) implementations; server binary with api/ingest/authd/migrate subcommands as separate processes and DB roles; NATS subjects agent.<id>.cmd, telemetry.<client>.<id>.*, result.<client>.<id>, shell.<id>.<sid>.*; TUF-inspired trust manifest.
