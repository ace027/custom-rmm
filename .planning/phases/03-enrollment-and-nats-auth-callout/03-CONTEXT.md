# Phase 3: Enrollment and NATS auth callout -- Context

## Key Design Decisions
- Database: migration 0002 creates tenant.client, tenant.site, tenant.device, tenant.agent, tenant.enrollment_token (all with client_id NOT NULL), msp.trust_artifact and msp.audit_event (append-only); function rmm.scope() returns uuid[] from current_setting('rmm.client_ids', true) and rmm.is_service() from current_setting('rmm.service', true) = 'on'; RLS ENABLE + FORCE on every tenant table with policy client_id = ANY(rmm.scope()) OR rmm.is_service()
- Roles: migration creates NOLOGIN roles rmm_api and rmm_authd (NOSUPERUSER NOBYPASSRLS) with least grants; services connect as the compose owner user and run SET ROLE <role> in sqlx after_connect, because the compose POSTGRES_USER is a superuser that would bypass RLS. Separate login roles come in phase 4
- rmm-db Scoped transactions: Scope::Clients(Vec<Uuid>) or Scope::Service(reason) set via set_config(..., true) inside the transaction; repositories take &mut Transaction and never the raw pool
- Shared enrollment types live in rmm_proto::enroll (EnrollRequest, EnrollResponse, HwFacts, Fingerprint with strength strong|weak) so agent and server compute the same fingerprint: SHA-256 over 'RMMFP1' || len-prefixed normalized SMBIOS UUID (lowercase, hyphenated), system serial and baseboard serial (trimmed, uppercased); junk values (all-zero/all-F UUID, 03000200-0400-0500-0006-000700080009, 'To be filled by O.E.M.', 'Default string', 'System Serial Number', 'Not Specified', '0', empty) make that part empty, and the fingerprint is weak if the UUID part is empty or both serials are empty
- Enrollment token: 'rmmenr_' + 32 chars of RFC 4648 base32 (no padding, 160 random bits); only SHA-256 stored; fields client_id, site_id, expires_at, max_uses, uses, allow_reattach, revoked; consumed atomically with UPDATE ... WHERE uses < max_uses AND NOT revoked AND expires_at > now() RETURNING
- Enrollment request is signed by the new agent key: proof = Ed25519 over b"RMMENROLL1" || SHA-256(canonical CBOR of the EnrollRequest without the proof field); server rejects ts outside +-300 s
- Reattach rules exactly as the design table: strong match + same client + old agent last_seen older than 24 h (or never) + token.allow_reattach -> reattach (old agent status superseded, device_event-style audit row); strong match with old agent seen within 24 h -> new device status pending_review with possible_clone_of; match in another client -> new device, flagged; weak fingerprint -> never reattach
- Technician auth: Entra ID OIDC bearer tokens (RS256) validated by rmm-api against the tenant discovery document and JWKS (cached 1 h, refetched on unknown kid), issuer https://login.microsoftonline.com/<tenant>/v2.0, audience RMM_ENTRA_AUDIENCE, app role claim roles containing RMM.Admin for token creation, revocation and trust uploads. A dev issuer (RMM_AUTH_DEV_PUBKEY_FILE + issuer 'rmm-dev') is accepted only when RMM_AUTH_ALLOW_DEV=1, logs a warning at startup, and is off by default; `rmm-server dev-token` mints dev tokens from RMM_AUTH_DEV_KEY_FILE for e2e tests
- Agent key: Ed25519 seed generated on device, stored by rmm_platform::KeyStore: Windows DPAPI CryptProtectData in the SYSTEM user scope (no CRYPTPROTECT_LOCAL_MACHINE) in %ProgramData%\RMM\agent.key with a protected DACL granting only SYSTEM full control (SDDL D:P(A;;FA;;;SY)); Linux/macOS a 0600 root-owned file in /var/lib/rmm (state dir overridable with RMM_AGENT_STATE_DIR for tests)
- NATS identity: the agent's Ed25519 public key is used as its NATS user nkey; authd verifies the nonce signature from the callout request's connect options and looks up the agent by credential_pubkey. Returned user JWT: expires 1 h, allowed_connection_types [WEBSOCKET], pub allow telemetry.<client>.<agent>.>, result.<client>.<agent>, shell.<agent>.*.out, svc.trust.latest, $JS.API.CONSUMER.MSG.NEXT.CMD.agent_<agent>, $JS.ACK.CMD.agent_<agent>.>; sub allow _INBOX_<agent>.>, shell.<agent>.*.in, shell.<agent>.*.ctl. Callout request xkey encryption is deferred (dev network only; only the authd user may subscribe to $SYS.REQ.USER.AUTH)
- Revocation: API POST /api/v1/agents/{id}/revoke sets status revoked and publishes rmm.internal.agent.revoked {agent_id, nkey}; authd (with SYS credentials) queries $SYS.REQ.SERVER.PING.CONNZ filtered by user nkey and calls $SYS.REQ.SERVER.<server_id>.KICK for each connection id
- All new workspace dependencies for this phase are added in plan 03-02 to the root Cargo.toml and to the crate manifests that will use them (so later plans in this phase do not edit Cargo.toml or Cargo.lock): reqwest (default-features off; rustls-tls, json), nkeys, jsonwebtoken (rust_crypto backend), data-encoding, uuid (v4, v7, serde), rand (os rng), windows features Win32_Security, Win32_Security_Cryptography, Win32_Security_Authorization, Win32_Storage_FileSystem, Win32_System_SystemInformation, Win32_System_Memory
- No Windows VM or real Entra tenant exists in CI or this sandbox: Windows-specific code is unit-tested on windows-latest (DPAPI round trip, SMBIOS parsing); the end-to-end flow runs with the Linux agent against the compose stack; 'Windows VM enrolls' and 'Entra login' are recorded as manual checks with runbooks
- Board quick-assess (pre-plan, 4.3/10, no artifacts yet) recommendations adopted: single-use expiring tokens, proof of possession, short-lived JWTs with minimal subjects, negative tests (stolen/expired token, cloned key, revoked agent, cross-tenant subject access), audit rows for each enrollment and callout decision, callout failure behaviour (deny on any error, 2 s DB timeout)
- Architecture proposals skipped (--auto, no spec assessment)

## Plan Structure
- **Plan 03-01 (Wave 1)**: Identity schema, RLS and repositories -- Add the client/site/device/agent/enrollment-token/trust-artifact/audit schema with RLS and roles, a Scoped transaction API in rmm-db, and tested repositories for enrollment, reattach lookup, agent status and trust artifacts.
- **Plan 03-02 (Wave 1)**: Device identity: key store, hardware facts and shared enrollment types -- Add the phase's dependencies, the shared enrollment wire types and fingerprint in rmm-proto, and the platform KeyStore (DPAPI on Windows, 0600 file elsewhere), hardware facts (SMBIOS on Windows, sysfs on Linux) and OS info in rmm-platform.
- **Plan 03-03 (Wave 2)**: Enrollment API, Entra auth and trust artifact upload -- Implement technician authentication (Entra OIDC with a gated dev issuer), enrollment-token creation, POST /v1/enroll with proof of possession and the reattach/clone rules, agent revocation, and verified trust-artifact upload in rmm-api, wired into rmm-server api.
- **Plan 03-04 (Wave 2)**: Agent enroll and connect -- Give the agent `enroll` and `run` commands: generate and store the device key, enroll over HTTPS with proof of possession, persist identity and trust bundle, and connect to NATS over WSS using its key as nkey, with reconnect backoff.
- **Plan 03-05 (Wave 3)**: NATS auth callout service and end-to-end enrollment -- Implement authd as a NATS auth callout that authenticates agents by nkey signature and DB status and issues scoped 1-hour WebSocket-only user JWTs, kicks revoked agents, switch the dev NATS config to auth callout, and prove the whole flow end to end with the Linux agent through nginx on 443.
