## Deferred (Medium Confidence)
- `crates/rmm-agent-core/src/shell_verify.rs (also crates/rmm-agent-core/src/shell.rs)` [major, 75%]: `verify_shell_open` takes `trust.techlist()` and never checks that the list is still unexpired (`expires_at`). `TrustStore::techlist()` is a plain getter. The expiry check (`check_time`) runs only when a list is installed, including from the cache at startup. `ShellManager::on_techlist` runs only on a trust update, so a running session is never re-checked when the list expires. A list that has expired in memory keeps authorising new shells and keeps existing ones open.
- `crates/rmm-agent-core/src/shell_verify.rs` [minor, 55%]: The grant id is written to the persisted replay cache (`seen` inserts it) before the technician, credential and assertion checks, and before the `MAX_SESSIONS` and spawn checks in `ShellManager::open`. A grant that is rejected for `too_many_sessions` or `spawn_failed` is consumed permanently. It cannot be retried with the same hardware signature until its `open_by` window expires, and the signed expiry is short.
- `crates/rmm-agent-core/src/shell.rs` [minor, 60%]: `open()` ignores the result of `ready_rx.recv_timeout(READY_TIMEOUT)` and returns `Ok(())`. If the subscribe takes more than 5 s or fails, the result already reported to the relay is "started", and the session then closes with `link_closed`.
- `crates/rmm-agent-core/tests/shell_session.rs` [advisory, 50%]: The 1 GB / 50 MB memory criterion is tested against a fake PTY (`TestPty::generating`) that generates output in-process and measures the test process's peak RSS. The real ConPTY/PTY blocking behaviour (a full PTY buffer blocking the child) is not exercised with 1 GB through the real `Pty` path here.
- `crates/rmm-agent-core/src/shell_verify.rs (with crates/rmm-agent-core/src/shell.rs)` [minor, 65%]: `seen()` inserts the grant id into the replay cache at line 200, before the technician, credential and assertion checks. `ShellManager::open` can still fail afterwards with `TooManySessions` or `SpawnFailed`, and those failures also leave the grant id in the cache.
- `crates/rmm-agent-core/src/shell.rs` [minor, 55%]: `set_window` accepts any relay-sent value, including 0 or anything below `max_chunk`. `can_take` then never holds (`unacked + pending + max_chunk <= window` is false), so the pump stops reading. Nothing ends the session except the liveness timeout, and a relay that keeps sending `Ping` can hold it open indefinitely.
- `crates/rmm-api/src/shell.rs` [minor, 55%]: The `ShellOpen` is published to JetStream before `tx.commit()`. If the commit fails, the agent can still open the shell while the DB says the session is `pending`, so the session is unrecorded. A retry then fails with `Replay`.
- `crates/rmm-api/src/relay.rs (with crates/rmm-api/src/shell.rs:48 and crates/rmm-agent-core/src/shell.rs:740-741)` [major, 60%]: The agent starts the shell and its liveness timer (45 s) as soon as it processes `ShellOpen`. The relay subscribes to `.out` and sends the first `Ping` only after the browser connects. The WS ticket is valid for 60 s (`TICKET_TTL_SECS`), longer than the agent's 45 s. A browser that connects between 45 s and 60 s gets a ticket that works against a session the agent has already closed. The `Closed{liveness}` message was published before the relay subscribed, and core NATS does not replay it. The relay then idles with a dead session. Browser Pong frames keep `last_rx` fresh, so the relay stays up until `max_duration` plus 30 s (up to 4.5 h). The status stays `opening` and the recording is unfinished.
- `crates/rmm-api/src/relay.rs` [major, 70%]: The relay contains the ack/credit logic, the recording hooks, the browser-silence handling and the Close/Closed behaviour. `grep` finds no automated test that drives `shell_ws` or `relay`. `crates/rmm-api/tests/shell.rs` stops at `open` and the recording download. It does not test a recording being written by a live relay, ack-after-send, or a recording failure closing the session. Only `scripts/e2e-shell.sh` exercises this path.
- `crates/rmm-platform/src/indicator.rs` [minor, 75%]: The unix socket is chmod'd `0o644`. Connecting to a unix-domain socket requires write permission on the socket file, so a non-owner user (the `rmm-session` helper in a user session) gets EACCES. The directory is also created with default permissions.
- `crates/rmm-platform/src/pty.rs` [minor, 60%]: If `try_clone_reader` or `take_writer` fails, the code silently substitutes `io::empty()` or `io::sink()`. The shell then runs with no output captured, so nothing is relayed or recorded. Input is discarded, or output is lost if only the reader failed. The session stays "open" until liveness. The error is neither logged nor returned.
- `crates/rmm-api/src/relay.rs and crates/rmm-api/src/shell.rs` [minor, 55%]: Sessions in `pending`, `opening` or `open` have no reaper. If the browser never connects, or the API process dies mid-relay, the row never reaches `closed`/`expired`. Only the `open_by` check at open time moves a `pending` row to `expired`. The 365-day purge deletes such rows without recording an end state.
- `.github/workflows/ci.yml, crates/rmm-agent-core/tests/shell_session.rs, scripts/e2e-shell.sh` [major, 75%]: The 1 GiB memory test only runs when `debug_assertions` is off. A grep of ci.yml for `release` and `shell_session` found nothing, so CI cannot run it. Debug builds use 64 MiB, and the e2e check prints 50 MB. The unit test uses a fake PTY and measures the whole test process's peak RSS. The real ConPTY/PTY path is never driven with 1 GB.
- `crates/rmm-api/src/relay.rs (with crates/rmm-api/src/shell.rs and crates/rmm-db/src/shell.rs)` [major, 75%]: The relay never times out waiting for the agent. If the agent rejects the `ShellOpen`, is offline, or dies mid-session, nothing arrives on `.out`. The relay only pings the browser and waits for the deadline, which is `max_duration` plus 30 s (up to about 4.5 h). The agent's rejection reason (such as `bad_assertion`) is not shown to the user.
- `crates/rmm-api/src/recording.rs` [minor, 60%]: The recorder has no size cap or disk quota. A grep of the file for MAX_/limit/cap found only the retention days and batch size. A 1 GB print becomes a roughly 1 GB or larger cast file, with JSON escaping inflating it.
- `crates/rmm-api/src/relay.rs; crates/rmm-api/src/shell.rs; crates/rmm-agent-core/src/shell.rs` [major, 65%]: The agent starts the PTY and its 45 s liveness clock when `ShellOpen` is processed. The relay subscribes to `.out`, creates the recording and sends the first Ping only when the browser connects with the WebSocket ticket, which stays valid for 60 s. Three consequences follow: - Output produced before the relay subscribes is core NATS, so it is lost. The recording and browser miss the initial prompt or banner. - A browser that connects after 45 s finds an agent session that already closed with `liveness`. Its `Closed` message was published to nobody. - In that case the relay never learns the session is dead. It holds the socket and recorder open until `max_duration` plus 30 s, up to about 4 h, and the DB row stays `opening`.
- `crates/rmm-api/src/shell.rs; crates/rmm-api/src/relay.rs` [major, 70%]: The API moves the session to `opening` and returns 200 after publishing the command. The agent's result, such as `bad_assertion`, `unknown_tech`, `too_many_sessions` or `expired`, never updates the `shell_sessions` row. A grep finds no consumer of the shell result. No timeout moves an `opening` session that no browser ever connects to to `closed` or `failed`.
- `crates/rmm-api/src/admin.rs` [major, 75%]: No Rust test covers the new `push_trust_update` path. A grep of crates/rmm-api for `TrustUpdate` finds only `admin.rs` itself; no test file under crates/rmm-api/tests (actions.rs, shell.rs) matches. Nothing checks that uploading a techlist publishes a correctly signed, correctly addressed command for each active agent. Nothing checks that other manifest or revocations kinds, duplicate uploads, or a missing key or NATS client behave as intended. The only coverage is the docker-based e2e script.
- `scripts/e2e-shell.sh` [minor, 55%]: Check (7) covers only the happy path: the agent is online and the first publish succeeds. It doesn't cover an agent that is offline during removal and reconnects, a duplicate upload, or a failed push. Check (1) publishes its techlist before the agent is enrolled, so that push path isn't tested there either.
- `crates/rmm-api/src/admin.rs` [major, 60%]: The update is published once per agent with a 24 h expiry. An agent that stays offline longer than that, or whose consumer is expired or recreated, never receives the techlist. The code publishes only at upload time and only to agents that are `active` at that moment. Nothing re-sends the current techlist when an agent reconnects or enrolls. Enrollment bundles are the only other path, and they only apply to new enrollments.
- `crates/rmm-api/src/admin.rs` [minor, 60%]: The push runs inline in the request handler. For each agent it does a sequential `ensure_agent_consumer`, a publish, and an await of the ack. The command is also built and signed per agent. `policy_hash` is hard-coded to 32 zero bytes with no named constant or comment. The command-building code duplicates what `actions.rs` already does for other commands, apart from the signing helper it reuses.
- `scripts/e2e-shell.sh` [advisory, 50%]: Check (4) now prints the full 1 GiB against the real agent and samples VmRSS and VmHWM. That fixes the real-agent half of F-005. The test in `crates/rmm-agent-core/tests/shell_session.rs` is still release-only, so CI does not run it.
