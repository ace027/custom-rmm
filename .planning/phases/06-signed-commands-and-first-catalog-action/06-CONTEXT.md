## Key Design Decisions
- Definition document: type rmm.definition/1, canonical CBOR, signed by the catalog role, identified by content_id (SHA-256 of payload); fields id (dotted name), version u32, title, capability (capability group, e.g. service, files.write), reversible bool, max_autonomy u8 (stored, not enforced until the autonomy gate), min_agent_version (semver), timeout_s (<= 900), params Vec<ParamSpec{name, kind: string|int|bool|enum, required, enum_values, max_len, min, max}>, precheck/steps/verify/rollback Vec<Step{block, args: BTreeMap<String, Arg::Lit(value)|Arg::Param(name)|Arg::Snapshot(key)>, retries <= 3, on_fail: abort|continue}>; at most 32 steps total; no loops or arbitrary execution by construction; deny_unknown_fields
- Static validation lives in rmm-recipe and runs on both sides: every block is in the agent's block registry, args match the block's arg schema, Param references exist and have the right kind, Snapshot keys are produced by an earlier snapshot step, retries and step counts within bounds, capability group of every block equals the definition capability or is listed as allowed by it
- Building blocks this phase: service.query{name}, service.stop{name, timeout_s}, service.start{name, timeout_s}, service.wait{name, state, timeout_s}, files.quarantine{root, pattern} (moves matching regular files from an allowlisted root into state_dir/quarantine/<cmd_id>/ with a manifest; never follows symlinks; root must be one of the platform's allowlisted roots: on Windows %SystemRoot%\System32\spool\PRINTERS), files.restore{} (restores this run's quarantine). Real services use the Windows SCM (windows crate, Win32_System_Services); Linux/macOS service blocks return Unsupported this phase
- Test mode for CI: in debug builds only, RMM_AGENT_TEST_PLATFORM=1 swaps in rmm_platform::fake::FakeServices (in-memory, preloaded with Spooler running; RMM_AGENT_FAKE_FAIL_START=<name> makes start leave it stopped) and adds an allowlisted test spool root under the state dir; release builds cannot enable it
- Spooler action (catalog/printing.spooler-restart.json draft, signed into the dev catalog): capability service; precheck service.query Spooler exists; snapshot: service.query (state) ; steps: service.stop Spooler, files.quarantine spool root *, service.start Spooler, service.wait running 30 s; verify: service.query == running; rollback: files.restore, service.start Spooler; reversible true
- Agent verification order (per design): TrustStore::verify_command (command role, agent/client binding, time window +-300 s, replay via the persisted Store ReplayCache, trust freshness) -> inline definition verify_role(Catalog) and not is_artifact_revoked(content_id) -> min_agent_version -> rmm-recipe static validation -> param validation against ParamSpec -> capability in manifest.capability_ceiling (the signed policy engine is a later product phase; until then the root-signed ceiling is the allow-list, recorded as a decision)
- Command intake: CMD stream (subjects agent.*.cmd, file storage, max_age 7 d, duplicate window 10 min, Nats-Msg-Id = cmd_id); per-agent durable pull consumer agent_<agent_id> filtered to agent.<agent_id>.cmd, created by the API at enrollment and lazily before issuing a command; the agent JWT also gets pub allow $JS.API.CONSUMER.INFO.CMD.agent_<a> so async-nats can bind to the consumer; the agent stores the envelope in a new encrypted Store inbox table before acking, then executes; one command at a time
- Result document: type rmm.result/1 signed by the agent's own key (ed25519-dalek directly, not rmm-trust's sign feature): {cmd_id, agent_id, definition_content_id, outcome: succeeded|failed|rolled_back|rejected, reason (for rejected: expired|replay|bad_signature|wrong_agent|revoked|unsigned_definition|validation|capability|stale_trust|agent_version), stages: [{stage: precheck|snapshot|steps|verify|rollback, ok, started_at, finished_at, detail <= 4 KiB}], finished_at}; published on result.<client>.<agent> through the outbox at priority 0 into the RESULT stream (max_age 14 d)
- Server side: migration 0005 adds msp.action_definition(content_id bytea pk, id, version, capability, envelope, uploaded_at, uploaded_by) and tenant.action_run(cmd_id uuid pk, client_id, agent_id, device_id, definition_content_id, params jsonb, requested_by, status queued|succeeded|failed|rolled_back|rejected|expired, reason, stages jsonb, result_envelope bytea, created_at, finished_at) with RLS and grants (rmm_api insert/select; rmm_ingest select/update status columns); PUT /api/v1/catalog (RMM.Admin, body = definition envelope, verified against stored trust like trust uploads), POST /api/v1/agents/{agent_id}/actions (RMM.Admin; body {definition_content_id hex, params}; validates params with rmm-recipe, signs Command{Invoke} with the server command key from RMM_COMMAND_KEY_FILE (32-byte seed, hex), expires_in 600 s, publishes to agent.<id>.cmd, inserts action_run queued, audits), GET /api/v1/action-runs/{cmd_id}; ingest gains a RESULT consumer that verifies the result signature with the agent's stored credential_pubkey and the result's agent_id/cmd_id binding, then updates action_run and writes audit_event (actor agent:<id>, action action.result)
- Negative-path tests in agent-side crates use golden fixture files generated by `cargo run -p xtask -- action-fixtures` (xtask may use rmm-trust's sign feature; it is not agent-side): valid, expired, replayed (same bytes twice), tampered (bit flip), revoked definition, definition signed by a non-catalog key, wrong agent, unknown block, bad param
- Dev trust: scripts/dev-trust.sh uses rmm-sign's file backend to create a dev root, catalog key and command key under deploy/dev/trust (gitignored), a manifest certifying catalog (+ artifact-revoke, techlist) and command, capability_ceiling [service, files.write], revocations, and the signed spooler definition; e2e builds the debug agent with RMM_ROOT_PUBKEYS from that dev root
- Windows reality check: test-windows runs an integration test that drives the real Spooler service through the SCM blocks (stop, start, query; the runner is an administrator); the full server -> agent spooler run on a Windows VM is a manual runbook check
- Board quick-assess (pre-plan, 4.0/10, missing artifacts) recommendations adopted: e2e of accepted and rejected paths, per-stage outcomes with timestamps and command id/definition hash in every result, negative-path tests for signature, replay, expiry, hash binding and wrong agent
- Spec skipped (no trigger); architecture proposals skipped (--auto)

## Plan Structure
- **Plan 06-01 (Wave 1)**: Recipe schema, validator, fixtures and phase dependencies -- Define the signed action definition and result documents, the static recipe and parameter validator in rmm-recipe, the spooler definition draft, the golden negative-path fixtures, and every dependency declaration this phase needs.
- **Plan 06-02 (Wave 2)**: Agent building blocks, command intake and executor -- Implement the service and files building blocks (Windows SCM, fake test platform), command intake from the per-agent consumer into the encrypted Store, the verification chain, the precheck/snapshot/execute/verify/rollback executor, and the agent-signed result published through the outbox.
- **Plan 06-03 (Wave 2)**: Catalog, command issuing and result ingest -- Add the action schema, catalog upload, the signed command issuing endpoint with per-agent JetStream consumers, and a result consumer that verifies agent-signed results and records action_run and audit rows.
- **Plan 06-04 (Wave 3)**: Dev trust bootstrap, end-to-end actions and CI -- Bootstrap a dev trust chain and signed spooler definition with rmm-sign, then prove end to end that a signed command runs the spooler recipe (success and rollback) and that a revoked definition is rejected, with recorded action_run and audit rows; add a Windows runbook.
