## Deferred (Medium Confidence)
- `crates/rmm-agent-core/src/store.rs` [major, 70%]: `inbox_put` uses `INSERT OR REPLACE ... state='pending'`. When JetStream redelivers a command, the row is rewritten as pending even if it is already `done`. Redelivery happens when the `+ACK` request fails (the code in commands.rs ~627 anticipates this) or when ack_wait expires. The command is then verified again, rejected as `Replay`, and a second signed result is queued for the same `cmd_id`.
- `crates/rmm-api/src/actions.rs` [minor, 60%]: `issue_command` checks only `def.capability` against the manifest ceiling. The agent's `verify` (commands.rs 285-302) also requires the capability group of every block the definition uses to be in the ceiling.
- `crates/rmm-api/src/actions.rs, crates/rmm-server/src/results.rs` [minor, 50%]: `issue_command` publishes to JetStream before `tx.commit()`. Two failure modes follow. (a) If the commit fails, the agent still runs a command that has no `action_run` row. (b) If the agent's result reaches the server before the commit is visible, `process_one` finds no run, counts `unknown_cmd` and returns `Term`. The result is dropped permanently and the run stays `queued`, later shown as `expired`.
- `crates/rmm-agent-core/src/commands.rs` [minor, 55%]: `process_pending` runs `handle`, which records the command in the replay cache and then executes it. If the process dies after that and before `inbox_mark_done`, the restart re-handles the row. That second pass is rejected as `Replay` and is not executed. The module docs describe this as "finishes (or rejects as a replay)", but nothing separates "already executed, result lost" from "never executed". When the first result was never queued, the server records `rejected/replay` for an action that actually ran.
- `crates/rmm-agent-core/src/commands.rs` [advisory, 60%]: `parse_hex32` is a hand-rolled hex decoder. `rmm_trust` and the platform hex helpers in `blocks.rs` (`crate::blocks::hex`) already handle hex, so encode and decode now live in different places.
- `crates/rmm-agent-core/src/executor.rs` [advisory, 65%]: Block metadata is looked up with a linear `BLOCKS.iter().find/any` on every step attempt. `commands.rs` 290-293 does the same lookup by name. The registry is queried by name in two modules with no shared accessor.
- `crates/rmm-agent-core/src/commands.rs` [advisory, 50%]: `envelope_ids` re-decodes the command envelope and the inline definition envelope, work that `verify` has already done. `accept` and `handle` each call it, so the same bytes are decoded up to three times per command.
- `.github/workflows/ci.yml` [major, 75%]: No CI step runs `cargo run -q -p xtask -- action-fixtures && git diff --exit-code crates/rmm-agent-core/tests/fixtures/`. A grep of `.github`, `scripts` and `docs` finds no reference to `action-fixtures`. The fixtures are generated by xtask, and the lint job does not check that they are current.
- `scripts/ci-local.sh` [minor, 70%]: The same `if ! run X; then docker compose logs; exit 1; fi` block is copied for each of four scripts: smoke-dev, e2e-enroll, e2e-telemetry and e2e-offline. This change adds a fifth copy for e2e-actions.
- `scripts/e2e-actions.sh` [minor, 60%]: The checks run in the order (1), (2), (4), (3). The header comment lists them as 1, 2, 3, 4, and the pass messages use the same labels. Check (4) reuses RUN1_ENV and RUN1_STATE from check (1) through globals. The reordering is needed because (3) stops agent-a and replaces the revocations, but the script never says so.
- `crates/rmm-api/src/actions.rs` [major, 70%]: `issue_command` publishes the command to JetStream before `tx.commit()`. The agent can pick up the command, run it and publish its result before the `action_run` row is visible. The results processor then finds no run, counts `unknown_cmd` and returns `Verdict::Term`. A failed commit after a successful publish also leaves a command that runs with no run row.
- `crates/rmm-platform/tests/windows_spooler.rs` [major, 60%]: The only automated Windows test of the real Spooler is `spooler_stop_and_start`. It exercises SCM stop and start only. The full pipeline on Windows (`files.quarantine` of the real spool directory, the executor stages, and the signed result) is covered only by the fake-platform e2e script on Linux and by a manual runbook. When the session is not elevated the test prints "skipping" and returns pass, and CI works around that by grepping the log.
- `crates/rmm-server/src/results.rs` [major, 70%]: `finished_at` comes from the agent-signed result as a bare `u64`, and `ActionResult::validate` does not bound it. `UNIX_EPOCH.checked_add(Duration::from_secs(n))` succeeds for any value up to about 2^63. The `.into()` to `DateTime<Utc>` then goes through chrono's `From<SystemTime>`, which unwraps `timestamp_opt`. That call panics for years beyond chrono's range (about 262143). The "falls back to now" comment only covers the `checked_add` failure, not this conversion.
- `crates/rmm-agent-core/src/commands.rs (with crates/rmm-agent-core/src/store.rs:480-495)` [major, 55%]: `accept` keys the inbox row on the `cmd_id` read from the unverified envelope, and `inbox_put` uses `INSERT OR REPLACE`. Any message delivered on the agent's subject with a known `cmd_id` and invalid contents overwrites the stored legitimate pending command. It also resets a `done` row to `pending`.
- `crates/rmm-api/src/actions.rs` [minor, 55%]: The server treats a definition as revoked if either its content id or the raw SHA-256 of its envelope bytes is revoked. The agent's `verify` checks only `is_artifact_revoked(&content_id)`.
- `crates/rmm-agent-core/src/commands.rs` [major, 65%]: The replay cache is written during verification. `queue_result` and `inbox_mark_done` happen only after execution. If the agent crashes or restarts mid-run, the inbox row is reprocessed and rejected as `Replay`. A `rejected/replay` result is then sent for a command whose steps may have partly run, for example the spool was quarantined and the service was stopped, and rollback never ran. The server records that as the final status, because `finish_action_run` only updates rows that are still `queued`.
- `catalog/printing.spooler-restart.json` [minor, 55%]: After a successful run, the quarantined spool files stay in `<state_dir>/quarantine/<cmd_id>/` indefinitely. No step or housekeeping purges them.
